What we actually tested in the router

We gave one prefiller two possible decoders: one nearby, one across the network. We measured when a locality rule should keep work nearby and when it should let traffic escape to the other decoder.

01
The machine

One prefill location. Two decode choices.

A prefiller reads the input prompt and creates its KV cache. A decoder uses that cache to generate the first and following output tokens. This experiment always chose the local prefiller first; the router's interesting decision was which decoder would receive the request.

What “local” means here: the decoder shares a physical host with the prefiller. It does not mean “the nearest region” or merely “a pod with a locality label.”
02
The method

First learn the trade-off. Then test policies on fresh traffic.

Think of calibration as trying both roads under known traffic. Once the settings were chosen, the comparison sent new requests and let each router policy make its own real decision.

Check 0 · Serving integrity

Prove both roads work

Six local and six remote real-model requests checked answers, worker identity, the packed cache layout and transfer lanes on all four receiving GPU ranks.

Stage 1 · Calibration

Measure each route on purpose

The client sent a diagnostic pin: “use local” or “use remote.” The router recorded the real chosen endpoint and rejected a request that escaped its pin.

Stage 2 · Held-out comparison

Let the policies decide

We froze settings, removed diagnostic pins, and ran the same traffic against five actual router configurations. No settings were tuned using these results.

Stage 1 · The four background-load states, each tested on both routes twice

4 load states × 2 forced decode routes × 2 repeats = 16 calibration episodes

Each episode added two foreground probes: one 4,096-token prompt and one 122,880-token prompt. Background requests generated 1,024 output tokens to keep decoders busy; foreground requests generated 32. We reversed local/remote route order on the second repeat to reduce order bias.

The diagnostic pin was placed before the router's saturation filter after an earlier run showed the filter removing a busy local decoder. This was a calibration-only repair; the five evaluated policy configurations stayed fixed.

Each cell sent four foreground probes (4K, 120K, 120K, 4K tokens). The low-load trace offered small background bursts; the high-load trace offered larger ones. The controller restarted/warmed each policy configuration, drained earlier requests, and saved each completed trial before proceeding.

03
The result

The new fixed allowance was slower than tuned soft locality.

The pre-set pass rule asked for more than 50 ms and 2% better mean first-token time in every matched block, with limited regressions. The result went the other direction in all three blocks.

Matched block verdict · allowance minus tuned soft
Held-out 1+0.581 s9.87% slower
Held-out 2+0.573 s9.75% slower
Confirmation+0.633 s10.77% slower
Pass criterion: failed. Positive time differences here are extra waiting for the allowance policy. The average matched difference was about +0.595 s, or 10.13% slower.
What seems to be happening

In the three high-load blocks, the allowance policy sent 6 of 12 foreground probes remote; tuned soft sent 3 of 12 remote. Across both load traces, 4K probes had observed mean first-token time of 1.46 s with allowance versus 0.29 s with soft. For 120K probes the means were close: 11.49 versus 11.47 seconds.

The extra remote choices and higher short-prompt latency occurred together. The aggregate data alone do not prove which part of routing, transfer, queueing or order caused every millisecond.

A subtle point: this does not erase the value of locality. A local KV transfer can be faster, yet a policy that decides when to preserve locality can still make worse whole-request decisions. Our comparison measured whole-request first-token time.
04
The implication

The fixed rule is not supported as a latency optimization here.

Engineering decision

Keep the negative result with the proposal.

The draft pull request adds a configurable routing behavior, but the tested fixed allowance did not improve first-token latency. The comparison against tuned soft locality should accompany maintainer review of whether that behavior is useful for another reason.

What the evidence supports next

Review the proposed policy with its measured trade-off

The completed run links decoder choices, client timing and KV transfers. It provides a concrete basis for deciding whether to retain the optional rule.

Distinguish transfer speed from routing quality

Local KV movement can be faster while a policy that favors locality makes worse end-to-end decisions under load.

Require fresh evaluation for a new rule

Prompt-dependent allowances and richer load signals remain hypotheses. Testing them would require a new prediction and new held-out traffic.

This result covers one model, topology and controlled traffic mix. It does not establish whether a different rule or workload would benefit from locality-aware routing.

Source of numbers: the frozen run report, analysis, and recomputation script. The draft pull request is still a draft. Scope: one model, one hardware placement, controlled traces; no statistical or production-wide claim.
