# Allocate both hosts before loading either model

The staged workflow originally protected spending while local CUDA-IPC serving was uncertain. Keeping that sequence after repeated successful local qualifications was an agent planning mistake: we paid to load and validate the first host before discovering the second could not be allocated. Rayhan identified that concurrent allocation can reduce total failed-attempt cost despite briefly exposing both hosts to billing. The two latest remote-capacity failures cost approximately$14.26 and$10.56; not all of either amount is avoidable, and no counterfactual savings are measured.

The runner now prepares CPU tooling, checks fresh capacity, prices both GPU hosts from the same conservative request timestamp and acknowledges the shortened cleanup deadline before requesting either host. One scoped Terraform apply targets both GPU node groups. The existing Terraform dependency graph confirms neither GPU group depends on the other; both share the cluster/fabric prerequisites. This allows concurrent requests, not an atomic capacity reservation or a guarantee of success.

During that apply, native status checks inspect both groups every10seconds and stop on either creation failure. No model is downloaded or loaded until both hosts pass health checks. Both model Pods are then submitted together; readiness checks cover both, allowing startup to overlap and detecting a failed remote Pod even while local startup is pending. All local and remote qualification checks still precede calibration and the unchanged five-policy evaluation.
